## 1. Что изменено в этой итерации

### 1.1. Ошибки, мешавшие запуску (по скриншотам и аудиту)

| Симптом | Причина | Исправление |
|---|---|---|
| Страница «Задачи»: `AttributeError: 'NoneType' object has no attribute 'splitlines'` (Windows) | `tasklist` пишет в кодовой странице консоли (cp866/cp1251); `subprocess.run(..., text=True)` падает при декодировании, `stdout` становится `None` | `tasks._alive` читает байты и декодирует с `errors="replace"`; `list_tasks` пропускает битую запись вместо падения страницы. Тест `test_tasks_windows.py` |
| В журнале экспериментов `laptop_gpu4`: **F1 = 0.000, precision 0, recall 0 на 31 клипе** | Профиль требует CUDA (`cuda:0`), на машине её нет → **каждый клип падал**, ошибка гасилась («клип без событий»), прогон сохранялся как «модель ничего не нашла» | (а) прогон, в котором не обработан **ни один** клип, больше не сохраняется в журнал — `RuntimeError` с первой ошибкой; (б) в журнале новая колонка `failed` (число клипов с ошибкой), чтобы частичный сбой не выглядел как плохая модель; (в) проверка устройства **до** прогона: `solver.check(devices=True)` → «профиль требует CUDA, а её нет», «OpenVINO-устройство недоступно», «пакет openvino не установлен». Включена в «Оценку», «Поток», `sd replay`, `sd monitor`, веб-приложение |
| `mvp`: F1 0.818 → 0.523 между прогонами при тех же 31 клипах | Не воспроизведено без данных пользователя. Возможные причины, которые теперь видны: клипы с ошибкой (`failed`), другой классификатор/пакет (отпечаток профиля и ноты прогона), изменившийся эталон (`gt_fingerprint`) | Сравнивайте `failed`, `fingerprint`, `gt_fingerprint` двух прогонов в журнале; если `failed > 0` — цифра неполная |
| Видео без числа кадров (wmv, ts, часть mkv): длительность 0 или отрицательная | `CAP_PROP_FRAME_COUNT` не заполнен | `video_io.probe` считает кадры проходом `grab()`, если счётчик ≤ 0 или нереалистичен |
| Видео не играет в браузере (wmv/avi/mkv/H.265, mp4v) | Браузеры играют H.264 в mp4 и VP8/VP9 в webm | Веб-приложение перекодирует один раз в `outputs/web_cache/*.mp4` (H.264, ≤ 960 px, faststart) в фоне; страница показывает «подготовка видео» |
| Профиль, подобранный под другое железо, молча роняет запуск | Нет предпроверки | см. выше: `solver.check(devices=True)` |

Предыдущие правки этой же ветки: обязательный классификатор, `fusion`, пакет решателя, replay, профили `stream_gpu4`/`stream_cpu6` — в [SOLVER_AND_STREAM.md](SOLVER_AND_STREAM.md).

### 1.2. Вывод видео (переписано)

Раньше формат выбирал сервер: H.264 в mp4 «на всякий случай». В браузерах без проприетарных кодеков (Chromium/Linux-сборки, часть корпоративных сборок) видео оставалось чёрным без объяснения. Теперь:

* **Формат выбирает клиент**: `canPlayType` → `h264` (mp4) или `vp9` (webm). Подходящий исходник отдаётся как есть, иначе один раз перекодируется в `outputs/web_cache` (с процентом готовности на странице).
* **Сбой не молчит**: если браузер всё же не принял файл (`video.onerror`), страница один раз пробует второй формат и иначе пишет код ошибки.
* Проверено в Chromium без H.264: файл `mp4v` воспроизводится через VP9 (раньше — чёрный экран).
* Камера играет **подряд**: по окончании фрагмента включается следующий; переход из тревоги («Открыть в камере») открывает нужный фрагмент за 3 с до события.

### 1.3. Анализ видео (переписан) и сокращение лишнего

* Три экрана вместо пяти: **Карта** (камеры и список — бывшая таблица «Камеры»), **Тревоги** (бывший «Журнал» — фильтр «решённые» + CSV), **Анализ видео**. Удалены: Streamlit-интерфейс оператора (`user_app.py`, `sd app --legacy`), страницы «Камеры» и «Журнал», кнопки демо вне пустого состояния.
* **Анализ в один шаг**: открывается последняя использованная папка и профиль (запоминаются), первое видео выбрано, готовый разбор подгружается сам. «Анализировать» — одно видео, «Всю папку» — очередь с таблицей состояния. В списке видео у каждого файла итог прошлого разбора (тревог, F1).
* **Управление просмотром**: ◀/▶ тревога (`[` `]`), пробел, ←/→ ±5 с, скорость ×0,5–×4, переключатели «рамки» (`B`) и «разметка», клик по таймлайну и по строке тревоги. Таймлайн: красное — тревоги, зелёное — разметка.
* Непригодный профиль помечен ⚠ с причиной (нет CUDA, нет openvino, нет классификатора) — кнопка неактивна, а не падает после запуска.

### 1.4. Архитектурные доработки

* **`fusion` работает в replay** (сигналы предмета и фото-модели действуют так же, как в offline; для VLM и для live — предупреждение, а не молчаливая разница). `ClassifierScorer` получает `fusion` из профиля.
* Профили проверяются на устройство перед запуском везде, где модель реально запускается.

### 2.2. Инварианты (нарушение = ошибка)

1. **Классификатор цикла обязателен** (`Profile.classifier_problem`, `solver.check`). Эвристика — только явным `allow_heuristic`.
2. **Вектор признаков классификатора не меняется** при подключении VLM/предмета/фото: они идут через `fusion` (поправка к логиту) или каскад `cycle_bundle_full`.
3. **Offline, replay и live — один код**. Различие только в источнике кадров и в том, какие признаки доступны (в live нет исходного файла → нет признаков предмета/фото).
4. **Порог не входит в отпечаток профиля** (применяется после прогона); веса и пакеты входят (sha256).
5. **Сбой клипа не прячется**: клип с ошибкой — пропуск с текстом ошибки; прогон без единого обработанного клипа не сохраняется.

## 3. Как строить решатель на каждом этапе

«Решатель этапа» — сменная реализация за единым контрактом; выбор определяется железом и режимом (`offline` / `replay` / `live`), а не вкусом. Рекомендации ниже — по результатам измерений MVP (см. [MVP.md](MVP.md)); числа на новых машинах **не измерялись**, проверять `sd replay` (`rt_factor ≥ 1.5`).

| Этап | Контракт (вход → выход) | Что выбирать | Не делать |
|---|---|---|---|
| **0. Источник** | папка/файл → кадры `(img, t)` с абсолютным временем | `sources.CaptureSource` для папок-камер; `Pacer` задаёт темп (0 / 1 / N) | не подменять время кадра номером кадра при VFR |
| **1. Поза + трекинг** | кадр → люди (рамка, 17 точек, ID) | **Главный рычаг качества — размер входа, а не размер модели**: YOLO26n/s-pose при `imgsz` 960–1280; BoT-SORT; уточнение RTMPose-s только при запасе по времени. GPU 4 ГБ: `yolo26s@1280` (CUDA); CPU/6 ГБ: `yolo26n@960` OpenVINO без уточнения | тяжёлые модели вместо большего входа; два модели позы одновременно |
| **2. Ряд признаков** | треки → `d_t` (кисть–рот в ширинах плеч), скорости, углы | один решатель (детерминированный, дешёвый); параметры — в конфиге | обучаемые модели здесь — дублирование этапа 5 |
| **3. Автомат циклов** | ряд → циклы (начало, пик, конец, пауза) | `cycles.find_cycles` с `th_in/th_out/hold`; подбирать на размеченных циклах | пороги «на глаз» без `oof-eval` |
| **4. Признаки цикла** | цикл → вектор | **live: только быстрые** (поза, пауза, ритм). **replay/offline: + предмет (детекторы на кропах кисть–рот), фото-модель**. VLM — только как надстройка (серая зона или fusion), не в live | включать в вектор классификатора то, чего нет в live (решатель с такими признаками для `live` отклоняется) |
| **5. Классификатор** | вектор → вероятность курения | `bundle`: LightGBM/logreg/MLP + изотоническая калибровка; `cycle_fast` для live, `cycle_mvp` для replay/offline. Всегда **один** обязательный; сигналы — через `fusion` с весами, подобранными на валидации | вес fusion > 0 без проверки на валидации; эвристика вместо классификатора |
| **6. Правила регламента** | оценки циклов → события | `events.build_events`: 2 цикла за 20 с или цикл + признак; склейка 15 с; порог события фиксируется до скрытого набора | менять правила под метрику |
| **7. Решение оператора** | тревога → подтверждено / ложная / не уверен | AlertStore + обратная связь → эталон → дообучение (этап 5) | считать решения оператора эталоном без разбора спорных |

Правило выбора между решателями одного этапа: берётся самый лёгкий, у которого **F1 на валидации не ниже на величину доверительного интервала** (в журнале есть `ci_lo/ci_hi`), и который проходит `sd replay` с `rt_factor ≥ 1.5` на целевом устройстве. Решатель собирается как профиль → пакуется `sd solver pack` → метаданные `solver.json` сами описывают, какие стадии и в каких режимах он поддерживает.

### Что лучше всего подходит под два ПК

| | ПК 1: 16 ГБ ОЗУ + GPU 4 ГБ | ПК 2: 6 ГБ ОЗУ |
|---|---|---|
| Поток | `stream_gpu4` (YOLO26s@1280 CUDA, RTMPose-s, 8 к/с, `cycle_fast`) | `stream_cpu6` (YOLO26n@960 OpenVINO, без уточнения, 6 к/с, `cycle_fast`) |
| Проверка/разбор | `laptop_gpu4` (`cycle_mvp`, детекторы предмета, фото-модель) | `laptop_cpu` по одному клипу |
| Если не успевает | снизить `imgsz` до 960 или модель до `yolo26n` | `pose.imgsz` 800, `video.process_fps` 5 |

## 4. Веб-приложение без Streamlit

Запуск: `sd app [--port 8502] [--host 0.0.0.0] [--open]`. Конфигурация камер: `streams/cameras.yaml`:

```yaml
gatchina-03: {lat: 59.5762, lon: 30.1291, street: "ул. Соборная", title: "Перекрёсток у вокзала"}
pavlovsk-01: {lat: 59.6905, lon: 30.4448, street: "Садовая ул."}
```

Без файла маячки раскладываются условно вокруг центра района (на карте помечено «схема», в таблице камер — «·схема»).

| Экран | Что делает |
|---|---|
| **Карта** (первый) | маячки камер: красный пульсирующий — есть тревоги без решения, зелёный — норма, серый — нет данных; клик по маячку или строке списка — выбор камеры (до 4) → «Смотреть выбранные». Без интернета автоматически схема (улицы и маячки в SVG), с интернетом — OpenStreetMap (Leaflet) |
| **Мультипросмотр** | до 4 видео, непрерывное воспроизведение фрагментов, таймлайн тревог камеры, «Разобрать моделью» → экран анализа с этим фрагментом |
| **Тревоги** | список + карточка (клип/кадр, уверенность, ID трека); «Подтвердить / Ложная / Не уверен» (Y/N/U) → следующая новая; фильтры по статусу и камере; «Открыть в камере»; журнал решений — те же фильтры + CSV |
| **Анализ видео** | см. §1.3 |

HTTP API (`web/server.py`): `GET /api/{health,stats,cameras,camera/<id>,folders,videos,profiles,alerts,alert/<id>,journal.csv,jobs,job/<id>,analysis,media-status,folder-of}`, `GET /media/video/<fid>?fmt=h264|vp9` (Range), `GET /media/alert/<id>/{thumb,clip}`, `POST /api/alert/<id>/review`, `POST /api/analyze` (`{video}` или `{folder}`), `POST /api/demo`.

Безопасность и устойчивость: идентификаторы файлов — непрозрачные (`<корень>|<относительный путь>`, base64), любой путь вне разрешённых корней (`streams`, `data`, `SD_WEB_ROOTS`) даёт 404; артефакты тревог отдаются только из `outputs/`; все пользовательские строки экранируются в DOM; сервер слушает `127.0.0.1` по умолчанию. **Аутентификации нет** — для сети только за обратным прокси с авторизацией.

Разработчику: фронтенд — `src/sd/web/static/` (vanilla JS, без сборки); логика без HTTP — `web/api.py` (тестируется напрямую); анализ видео — очередь из одного потока (одна модель в памяти за раз, важно для 6 ГБ).

## 5. Проверка

* `pytest`: 368 прошли, 7 пропущены (нет данных/весов). Веб: `test_web_api` — реальный HTTP-сервер (камеры и координаты, Range 206/416, перекодирование и выбор формата h264/vp9, защита от путей `../`, цикл решения оператора, очередь анализа по видео и по папке, итог прошлого разбора в списке, ошибка задачи без моделей); `test_tasks_windows`; `test_runner` (все клипы упали → не в журнал); `test_review_fixes` (fusion в replay).
* Браузер (Chromium, Playwright), сценарий целиком: карта → выбор камеры → мультипросмотр (**mp4v играет через VP9**, раньше чёрный экран) → «Анализ видео»: автовыбор, готовый разбор, ◀/▶ тревога, клавиша `B`, **оверлей совпал с видео** (красные пиксели рамки и баннера в нужный момент), таймлайн с разметкой и тревогами; ошибок JS нет.
* **Не проверено:** реальные модели позы на реальных записях (в среде нет весов и CUDA/OpenVINO) — поэтому в браузерных проверках кнопка «Анализировать» неактивна, а разбор подставлялся заранее; результат реальной модели в веб-очереди проверен только заглушкой и сценарием «нет модели → понятная ошибка»; Leaflet с реальными плитками; скорость на двух целевых ПК.

## 6. Ограничения и план

1. Живой видеопоток в браузере (HLS/WebRTC) не сделан: камеры — папки с фрагментами (по ТЗ MVP). Следующий шаг — отдача сегментов `m3u8` из того же сервера.
2. Тревоги из `sd monitor` показываются опросом раз в 5 с (SSE/WebSocket — следующий шаг).
3. Положение камер — вручную в `cameras.yaml`; редактор на карте (перетаскивание маячка) не сделан.
4. Нет аутентификации и ролей оператора (только имя в журнале).
5. В live нет признаков предмета/фото/VLM, поэтому fusion там не действует (предупреждение); VLM в replay не считается — нужна очередь VLM.
6. Интерфейс разработчика (`sd ui`) остаётся; перенос на ту же веб-платформу — после стабилизации API.
