## 1. Общая схема

```
                          ┌──────────────────────────── данные ─────────────────────────────┐
 камеры = папки           │ streams/<район>-<индекс>-<время>/*.mp4    data/…    labels/*.csv │
                          └──────┬─────────────────────────────────────────────┬────────────┘
                                 │ realtime.sources (фрагменты, абс. время)    │ runner.evaluate_dirs / pipeline.recognize
                                 ▼                                             ▼
 ┌──────────── ОДИН И ТОТ ЖЕ код признаков, циклов и событий (offline = replay = live) ─────────────┐
 │ 1 поза+трек ─► 2 ряд d_t ─► 3 автомат циклов ─► 4 признаки цикла ─► 5 КЛАССИФИКАТОР ─► 6 правила │
 │ pose_track     features      cycles.find_      быстрые + предмет    bundle (+fusion)    events.   │
 │ tracks         .build_series cycles            + фото + VLM                             build_    │
 └──────────────────────────────────────────────────────────────────────────────────────────────────┘
        │ realtime.StreamEngine (буфер 90 с)                   │ evaluation (Event F1, ±3 с, IoU ≥ 0.3)
        ▼                                                      ▼
 AlertStore (SQLite WAL) ◄── worker (sd monitor)        experiments (журнал прогонов, отпечатки, заметки)
        │                                                      │
        ▼                                                      ▼
 web (sd app, :8502): карта, тревоги, анализ видео      Dev Studio (sd ui, Streamlit): валидация, аналитика,
        │ решения оператора                             конструктор, задачи, данные, модели, профилирование, выпуск
        └──► realtime.feedback ──► labels/events_gt.csv ──► обучение ──► пакет ──► решатель / выпуск
```

Хранилище тревог в схеме — прежний SQLite-файл или (при `SD_DB_URL`) БД платформы; поверх неё работает API платформы (`sd serve`, :8503) для веба и интеграций — раздел 5.3.

Схема конвейера с моделями профиля `mvp` — [img/platform/d02_pipeline.svg](img/platform/d02_pipeline.svg). Живая схема с подсветкой правок — вкладка «Конструктор» Dev Studio (`arch.dot`).

## 2. Конвейер распознавания

| этап | вход → выход | модуль | профиль `mvp` |
|---|---|---|---|
| 0. Источник | файл или папка → кадры `(img, t)` | `video_io`, `realtime.sources` | 5 к/с (`video.process_fps`) |
| 1. Поза и трек | кадр → люди: рамка, 17 точек, ID | `pose_track`, `tracks` (склейка офлайн) | YOLO26n-pose@960 (OpenVINO iGPU) + BoT-SORT; уточнение RTMPose-s, когда рука у лица |
| 2. Ряд признаков | треки → `d_t` (кисть–рот в ширинах плеч), скорости, углы | `features.build_series` | рот = нос + 0.35·(плечи − нос), сглаживание |
| 3. Автомат циклов | ряд → циклы REST → APPROACH → AT_MOUTH → RETRACT | `cycles.find_cycles` | вход 0.65 / выход 0.90, пауза 0.5–5 с |
| 4. Признаки цикла | цикл → вектор | `pose_feats` (быстрые), `evidence` (предмет), `photo_video`/`photo_feats` (CLIP), `vlm` | Beehzod + basant18 на кропе рта, zero-shot CLIP |
| 5. Классификатор цикла | вектор → вероятность затяжки | `bundle`, `classifier`, `fusion` | пакет `cycle_mvp` (ансамбль, набор `obj_hold_zsd`) |
| 6. Правила события | оценки циклов → события | `events.build_events` | 2 цикла за 20 с или цикл + прямой признак; склейка ≤ 15 с; людей ниже 80 px — IGNORE |

Сквозные функции:
- офлайн — `pipeline.recognize` (один клип) и `runner.evaluate_dirs` (папки);
- признаки предмета, фото и VLM по уже найденным циклам — `enrich`.

### 2.1. Кэш этапов

Все артефакты — в `outputs/` (`SD_OUTPUTS`). Каждый этап кэшируется по хэшу своих параметров. Поэтому подбор порогов не пересчитывает позу:

| что | где | ключ |
|---|---|---|
| поза и трек | `runs/<video_id>/<run_id>/pose/` | `run_id`: интервал + `video.process_fps` + `pose.*` + `tracking.*` |
| ряд признаков | `…/features/<hash>/series.parquet` | секция `features` |
| циклы | `…/cycles/<hash>/` | `features` + `cycles` |
| события | `…/events/<hash>/events.csv` | `events` + минимальный рост |
| признаки цикла | `enrich/…` | цикл + подпись детекторов, фото-пакета, модели VLM |
| результат клипа | `recognize/…` | профиль |

Цену правки параметра (что пересчитается) вычисляет `arch.impact`. Её показывает «Конструктор»; уровни описаны в [DEV_STUDIO.md](DEV_STUDIO.md).

### 2.2. Конфигурация и профили

- `configs/default.yaml` — все 99 параметров. Комментарий в строке параметра — его описание; его читают и конвейер, и подсказки конструктора (`arch.parse_defaults`).
- Профиль `configs/experiments/<имя>.yaml`:
  - переопределения конфигурации;
  - `options`: `cycle_bundle`, `objects`, `photo_bundle`, `vlm_model`, `fusion` и др.

  Методы: `profiles.Profile.cfg()` и `opts()`. Метод `fingerprint()` — отпечаток: конфигурация + sha256 весов и пакетов; порог в отпечаток не входит.
- Рабочий профиль — `mvp.yaml`. Прежние лежат в `configs/experiments/archive/`: `baseline`, `laptop_cpu`, `laptop_gpu4`, `stream_cpu6`, `rt_candidate`, `mvp1`, `mvp_old`. Вернуть профиль — скопировать файл на уровень выше.
- Временные правки без файла: `profiles.with_overrides(base, ["pose.imgsz=1280", "options.vlm_mode=\"grey\""])`. Их используют `sd eval -s …` и конструктор.
- Спецификации классификатора (набор признаков, модель, CV) — `configs/classifiers/*.yaml` (`SD_CLASSIFIERS`).

### 2.3. Классификатор цикла

- **Обязателен.**
  - Единая проверка — `Profile.classifier_problem()`. Её делают `recognize`, `sd eval`, `sd monitor`, `sd replay` и Dev Studio.
  - Без классификатора есть только эвристика по длительности паузы. Она не отличает питьё и телефон, поэтому включается лишь явным `options.allow_heuristic: true` (отладка и тесты).
- **Пакет** `models/cycle/<имя>/` — без pickle:
  - модель;
  - изотоническая калибровка;
  - список признаков;
  - манифест: набор признаков, источник таблицы (прогон), отпечаток меток, список видео обучения (`bundle.training_videos`).
- **Обучение по спецификации** (`classifier.py`):
  1. таблица циклов из конкретного прогона (`oof_eval.collect(from_run=…)`);
  2. диагностика переобучения: разрыв train−oof, перестановка меток, кривая обучения;
  3. обучение;
  4. вложенная oof-оценка (`sd oof-eval`).

  Устаревший путь — `train.py` / `sd train` (joblib). В коде он остаётся только для совместимости.
- **Слияние** (`options.fusion`, `fusion.py`) — поправка к логиту по сигналам `vlm_yesno`, `photo_p_mean`, `obj_any_max_conf`:
  `logit' = logit + clip(Σ wᵢ·(sᵢ − refᵢ), ±clip_logit)`.
  Вектор признаков классификатора при этом не меняется. При нулевом весе или отсутствии сигнала оценка прежняя.
- **Каскад «серая зона → VLM»**: `cycle_bundle_full`, `vlm_mode: grey`.
- **Утечка обучения в оценку.** `bundle.leak(bundle, clips)` — пересечение видео обучения с клипами оценки. Где это используется:
  - `evaluate_dirs` предупреждает, а на роли `hidden` отказывает;
  - Dev Studio показывает утечку в чек-листе, в результате и в PDF;
  - ворота выпуска не пропускают такой пакет.

### 2.4. Оценка

- `evaluation` / `evaluate` — Event F1 по протоколу организаторов. Совпадение: ±3 с по интервалу, IoU ≥ 0.30 рамок в `peak_sec`, сопоставление один к одному. IGNORE не штрафуется.
- Порог события подбирается на кривой (`policy=fixed | tuned`). Для роли `hidden` порог фиксируется до прогона.
- Журнал прогонов — `outputs/experiments/<id>/`:
  - `summary.json`, `per_clip.csv`, `curve.csv`, `errors.csv`, `timing.csv`;
  - копия профиля;
  - `notes.json` — тег, заметка, закрепление из Dev Studio.

  Индекс строит `experiments.list_runs`, каталог с действующими параметрами — `compare.catalog`.
- Доверительные интервалы — bootstrap по клипам. Парное сравнение двух прогонов — `sweep.compare_saved`.
- Прогон, в котором не обработан ни один клип, не сохраняется. Клип с ошибкой — пропуск с текстом ошибки.

### 2.5. Инварианты

Нарушение любого из них — ошибка.

1. Классификатор цикла обязателен; эвристика — только явным `allow_heuristic`.
2. VLM, предмет и фото не меняют вектор признаков классификатора: они идут через `fusion` или каскад.
3. Offline, replay и live — один код. Различаются только источник кадров и доступные признаки: в live нет исходного файла, а значит нет предмета и фото.
4. Порог не входит в отпечаток профиля; веса и пакеты входят (sha256).
5. Сбой клипа не прячется; пустой прогон не сохраняется.
6. Пути в артефактах — переносимые (`$DATA/…`, `$OUTPUTS/…`, `paths.portable` / `from_portable`), без абсолютных путей машины.

## 3. Поток: монитор, replay, тревоги

Один алгоритм в двух режимах. Офлайн — для оценки; поток — для демонстрации и внедрения. Движок **не переписывает** алгоритм в потоковом виде: он запускает тот же офлайн-код на скользящем буфере. Тест `test_stream_matches_offline_event_on_same_input` проверяет, что событие совпадает до кадра.

### 3.1. Камеры-папки

Камера — это папка с видеофрагментами. Имя папки строится по шаблону **`<район>-<индекс>-<время начала>`**, например:
- `gatchina-03-20261009T143000`;
- `gatchina_03_2026-10-09_14-30-00`;
- `tsarskoe-selo-12-1430` — только время, дата берётся текущая.

Имя не по шаблону запуск не ломает: район = имя папки, индекс 0, время = дата файла.

Фрагменты сортируются естественно (`part2` < `part10`). Абсолютное время кадра = начало + сумма длительностей предыдущих фрагментов + время в фрагменте.

Режим `--watch` подхватывает новые фрагменты. Каталог камер — `streams/` (`SD_STREAMS`); координаты камер — `streams/cameras.yaml`.

### 3.2. StreamEngine (`realtime/engine.py`)

- **Кадр.** `step(img, t)` → `pose_fn` → детекции попадают в буфер последних 90 с (`buffer_sec`).
- **Раз в секунду потока** (`eval_every_sec`) по буферу пересчитываются ряд и циклы. В работу берутся только закрытые и «осевшие» циклы — те, что закончились раньше чем `settle_sec = 1 с` назад. Циклы, обрезанные началом буфера, игнорируются.
- **Оценка** (`realtime/scoring.py`):
  - `ClassifierScorer` — пакет из профиля; `fusion` действует в replay;
  - `HeuristicScorer` — только при `allow_heuristic`.
- **Тревоги.**
  - `open` — правило выполнено и уверенность ≥ порога. Начало события — подъём руки в первом цикле. Тревога приходит при подтверждении, обычно через 5–15 с после начала курения (две затяжки) плюс 1–2 с «оседания».
  - `update` — событие продлилось. Обновляются конец и уверенность; решение оператора сохраняется.
  - `close` — через `merge_gap` (15 с) без новых циклов.
- **Память ограничена.**
  - Буфер — 90 с.
  - `FrameRing` — 45 с JPEG 640 px (≈ 10 МБ), для миниатюр и клипов ±5 с.
  - Старое состояние очищается (`test_engine_state_stays_bounded_over_long_stream`).
- **Журнал циклов** (`cycle_log`) — оценки, сигналы и поправки fusion для каждого цикла. Ключевые точки по кадрам (`last_kps`) идут в трассу и живой поток веба.

### 3.3. Режимы

| режим | команда | источник | признаки цикла |
|---|---|---|---|
| offline | `sd eval`, `sd recognize`, `python -m sd.run` | файл целиком | все (поза, предмет, фото, VLM) |
| replay | `sd replay clip.mp4 [--speed 1] [--gt] [--render]`, Dev Studio «Валидация → Поток» | файл через `StreamEngine` | все, кроме VLM; `fusion` действует |
| live | `sd monitor [--watch] [--speed N] [--camera …]` | камеры-папки | только быстрые (поза, пауза, ритм) |

Что сохраняет replay (`outputs/replay/<время>_<клип>/`):
- `events.csv`, `alerts.csv`, `log.csv`, `summary.json`;
- при `--gt` — TP/FP/FN и задержка тревоги;
- `rt_factor` = секунды видео / секунды вычислений. Значение ≥ 1 — успевает; целая часть ≈ число камер на машину.

`sd solver check <имя> --mode live` отклоняет решатель, которому нужны признаки, недоступные в потоке.

### 3.4. Хранилище тревог

По умолчанию — файл `outputs/monitor/monitor.db` (SQLite WAL, `SD_MONITOR_DB`). Пишет воркер, читает веб; это разные процессы. При заданном `SD_DB_URL` вместо него используется БД платформы (`SqlAlertStore`, 5.3): те же операции, плюс история решений и пользователи; схема и перенос — [API.md](API.md), раздел 6–7. Таблицы ниже — прежнего хранилища.

| таблица | содержимое |
|---|---|
| `cameras` | район, индекс, папка, время начала, статус, последняя активность, обработано секунд |
| `chunks` | обработанные фрагменты со смещением (перезапуск продолжает с первого необработанного) |
| `alerts` | ключ `<камера>:<ID>:<начало>`; время события и тревоги; уверенность; рамка; правило и объяснение; `status` (`new` → `confirmed` / `false` / `unsure`); оператор; время решения; заметка; миниатюра; клип; отпечаток профиля; признак `demo` |

Обратная связь — `sd feedback-export` (`realtime/feedback.py`). Решения оператора переносятся в `labels/events_gt.csv`:
- подтверждённые — как POSITIVE с рамкой;
- ложные — как NEGATIVE (жёсткие негативы).

Повторный экспорт не создаёт дубликатов. Файл эталона защищён блокировкой.

### 3.5. Ограничения потока

| что | последствие | план |
|---|---|---|
| нет склейки треков постфактум (в офлайне есть, `tracks.stitch_tracks`) | смена ID делит эпизод на 1 TP + 1 FP | онлайн-склейка по рамке и времени |
| в live только быстрые признаки | хуже различает питьё и телефон, чем офлайн | кропы из `FrameRing` → очередь предмета и фото |
| сглаживание центрированное (0.2–0.5 с вперёд) | тревога запаздывает на это время | заложено в «оседание» |
| воркер обрабатывает камеры последовательно | скорость делится на число камер | процесс на камеру (`--camera`), батчинг |
| после перезапуска состояние потока теряется | жест на стыке может не засчитаться | допустимо для MVP |
| `realtime.sources.CaptureSource` (RTSP / веб-камера, очередь 3 кадра со сбросом старых) не подключён к `sd monitor` | реальные камеры не подключаются | подключить с метками времени источника |

## 4. Решатель и выпуск

### 4.1. Решатель `*.sdsolver.zip` (`solver.py`, `cli_solver.py`)

Полный конвейер одним архивом для другого устройства:

```bash
sd solver pack mvp --name mvp_v1 --with-weights --with-dataset --run <id_прогона>
sd solver inspect mvp_v1.sdsolver.zip
sd solver install mvp_v1.sdsolver.zip [--overwrite]
sd solver check mvp_v1 --mode live
```

- **Состав архива:**
  - `solver.json`;
  - `profile.yaml`;
  - пакеты `bundles/<cycle|photo>/<имя>/<файл>`;
  - по желанию — веса и набор разметки.

  Все пути переносимые, у каждого файла sha256.
- **`solver.json → architecture`:**
  - режим (`classifier`, `classifier+fusion`, …);
  - стадии и модель каждой (с sha256 весов);
  - признаки классификатора;
  - оценка ресурсов;
  - допустимые режимы `offline` / `replay` / `live`;
  - качество на момент упаковки;
  - отпечаток профиля.

  По этим данным `check` (с `devices=True` — ещё и проверка устройств: CUDA, openvino) решает, годится ли решатель.
- **Безопасная установка:**
  - члены архива проверяются (`_safe_member`: без абсолютных путей, `..` и ссылок);
  - sha256 сверяется до записи;
  - распаковка идёт во временный каталог и переносится целиком;
  - существующее не перезаписывается без `--overwrite`;
  - архив без классификатора или с `allow_heuristic` не устанавливается.
- **Куда ставится:**
  - пакеты → `models/<kind>/<имя>`;
  - профиль → `configs/experiments/<имя>.yaml`;
  - решатель → `models/solvers/<имя>/`.
- **Ограничение:** `solver.json` сам по себе не подписан. sha256 защищает от повреждения, но не от пересборки злоумышленником — подписывается выпуск (4.2).

### 4.2. Выпуск (`release.py`, Dev Studio «Выпуск»)

Ворота качества по выбранному прогону:
- F1 и его нижняя граница не ниже заданных;
- роль прогона;
- нет утечки обучения;
- есть классификатор;
- предупреждение о лицензиях (Ultralytics AGPL-3.0).

Затем:
1. упаковка решателя;
2. PDF-отчёт прогона;
3. `outputs/releases/<имя>/release.json` — метрики, отпечатки, git, sha256 архива и подпись HMAC-SHA256, если задан `SD_RELEASE_KEY`.

Проверка выпуска — `release.verify`.

### 4.3. Как выбирать модель этапа

«Решатель этапа» — сменная реализация за контрактом из раздела 2. Выбор определяется железом и режимом.

| этап | что выбирать | чего не делать |
|---|---|---|
| поза | **главный рычаг — размер входа, а не размер модели**: YOLO26n@960 близко к лучшему; для дальних людей (≈ 130 px) — 1280–1600; RTMPose-s — при запасе по времени | тяжёлые s/m/x вместо большего входа: на замерах они не нашли больше затяжек |
| ряд и автомат | детерминированный, параметры в конфиге; пороги — по размеченным циклам (`sd oof-eval`, «Аналитика → Ошибки и порог») | пороги «на глаз» |
| признаки цикла | live — только быстрые; replay и offline — + предмет и CLIP; VLM — только надстройка (серая зона или fusion) | включать в вектор то, чего нет в целевом режиме |
| классификатор | короткие наборы (`obj_hold_zsd`, 6 признаков); выбор по вложенной oof-оценке | длинные наборы на ≈ 200 циклах — переобучение (`full`, 42 признака, хуже) |
| правила | регламент; порог события фиксируется до скрытого набора | менять правила под метрику |

Правило выбора: самый лёгкий вариант, у которого F1 не ниже лучшего на величину доверительного интервала и `rt_factor ≥ 1.5` на целевом устройстве. Сравнение — «Аналитика → Сравнение подходов / Влияние параметров»; скорость — «Профилирование».

### 5.2. Веб-приложение оператора (`sd app`, порт 8502)

Сервер `http.server` из стандартной библиотеки (`web/server.py`, только `127.0.0.1` по умолчанию). Логика без HTTP:
- `web/api.py` — камеры, видео, тревоги, анализ;
- `web/admin.py` — профили, реестр, передача;
- `web/tuning.py` — оценка и подгонка.

Фронтенд — vanilla JS без сборки (`web/static/`).

Видео:
- клиент выбирает формат через `canPlayType` (h264 или vp9);
- остальное перекодируется один раз в `outputs/web_cache/`;
- отдача с поддержкой Range.

Безопасность сейчас:
- идентификаторы файлов непрозрачные; путь вне разрешённых корней (`streams`, `data`, `SD_WEB_ROOTS`) даёт 404;
- имя профиля из браузера проходит через `profiles.load_named`;
- строки экранируются в DOM;
- **входа, ролей и CSRF-защиты нет**;
- Leaflet и тайлы карты грузятся с внешних CDN.

Экраны и API — [WEB_APP.md](WEB_APP.md). Это прототип; его заменяет веб-интерфейс `/app` на бэкенде с входом и ролями (5.3): [WEB_UI.md](WEB_UI.md).

### 5.3. Бэкенд платформы (`sd serve`, порт 8503)

Пакет `src/sd/server` — FastAPI + SQLAlchemy 2 + Alembic. Полное описание — [API.md](API.md); здесь — место в архитектуре.

```
routers/ (system, auth, users, cameras, alerts, analysis, dev)  →  services/ (users, alerts, cameras, audit, artifacts)  →  models.py + migrations/  →  SQLite | PostgreSQL
                                   └─ делегирует прежним модулям: web.api.WebApp, web.admin, tasks, experiments, compare, labels_history, release
```

- **Что даёт сверх прежнего приложения:** вход и роли (viewer < operator < developer < admin), API-токены, журнал действий, неизменяемую историю решений, камеры с городом и координатами, страницы и фильтры, поток обновлений SSE, доступ к функциям Dev Studio (профили, журнал прогонов, задачи, разметка, выпуски) без Streamlit.
- **Хранилище мониторинга.** `SqlAlertStore` повторяет интерфейс `realtime.store.AlertStore`; `realtime.store.open_store()` выбирает его при заданном `SD_DB_URL`. Воркер, демо, обратная связь и прежнее приложение работают с БД платформы без правок.
- **Схема только через миграции** (`sd db …`, цепочка `0001_identity` → `0002_monitoring`); тест следит, чтобы миграции не расходились с моделями; для PostgreSQL миграции проверены как SQL.
- **Что не заменено:** распознавание, обучение и Dev Studio остаются в прежних модулях; интерфейс оператора (`sd app`) пока на прежних маршрутах.
