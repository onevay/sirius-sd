# Мониторинг и real-time контур

> Состояние на 8 октября 2026: **MVP-каркас**. Работает на имитации камер (папки с видео), без обязательного GPU и без внешних сервисов. Проверено тестами на синтетическом человеке и настоящих видеофайлах; **с реальными моделями позы на реальных записях контур не запускался** (в среде разработки нет весов) — первый прогон на вашей машине нужно сделать с `--speed 0` на коротком фрагменте и сверить с offline (см. [«Первый запуск»](#первый-запуск)).

## 1. Что это и зачем

Руководство (§8) требует: один алгоритм в двух режимах — offline для оценки и real-time для демо и внедрения, чтобы цифры скрытого набора честно описывали и поток. Здесь это сделано так:

```
папки-камеры ──► воркер ──► StreamEngine (на камеру) ──► тревоги ──► SQLite ──► приложение оператора
 район-индекс-       │            │  поза+трекинг (PoseTracker.step)            │      подтвердить / ложная
 время начала        │            │  буфер 90 с → ряд признаков → автомат циклов │            │
                     │            │  → оценка цикла → правила регламента         ▼            ▼
                     └─ миниатюра и клип ±5 с                                 эталон и обучение (sd feedback-export)
```

Ключевое решение: движок **не переписывает алгоритм в потоковом виде**, а запускает тот же offline-код (`features.build_series`, `cycles.find_cycles`, `events.build_events`) на скользящем буфере последних 90 секунд. Поэтому поток и offline дают одно и то же событие на одном входе — это проверено тестом `test_stream_matches_offline_event_on_same_input` (границы совпадают с точностью до кадра).

## 2. Камеры-папки (имитация реальных данных)

Камера = папка с видео-фрагментами. Имя папки: **`<район>-<индекс>-<время начала>`**.

| имя папки | район | камера | начало |
|---|---|---|---|
| `gatchina-03-20261009T143000` | gatchina | 03 | 2026-10-09 14:30:00 |
| `gatchina_03_2026-10-09_14-30-00` | gatchina | 03 | то же |
| `tsarskoe-selo-12-1430` | tsarskoe-selo | 12 | сегодня 14:30 (только время — дата берётся текущая) |
| `Гатчина-7-14-30-15` | Гатчина | 7 | сегодня 14:30:15 |

Имя не по шаблону не ломает запуск: район = имя папки, индекс 0, время = дата файла (в интерфейсе разработчика такие папки помечены). Фрагменты внутри папки идут по имени с естественной сортировкой (`part2` < `part10`); **абсолютное время кадра = время начала + сумма длительностей предыдущих фрагментов + время в фрагменте**. Папку можно пополнять новыми фрагментами в любой момент — режим `--watch` подхватывает их и продолжает поток с правильным смещением.

Каталог камер — `streams/` в проекте или `SD_STREAMS` (`.env`). Пример:

```
streams/
  gatchina-03-20261009T143000/   part1.mp4  part2.mp4  part3.mp4
  pavlovsk-01-20261009T100000/   a.mp4  b.mp4
```

## 3. Запуск

```bash
# 1) воркер: обработать то, что есть, и выйти / следить за папками
sd.cmd monitor --streams streams --profile final               # Windows;  Linux/macOS: ./sd.sh monitor …  или  make monitor
sd.cmd monitor --watch --speed 1                               # как в реальном времени (--speed 4 — вчетверо быстрее, 0 — без пауз)
sd.cmd monitor --camera gatchina-03 --camera pavlovsk-01       # только эти камеры

# 2) интерфейс оператора (отдельный процесс, порт 8502)
sd.cmd app

# 3) пока нет моделей/записей — демо-данные для работы над интерфейсом (помечены «ДЕМО»)
sd.cmd monitor-demo --n 14          # создать;   sd.cmd monitor-demo --clear — удалить

# 4) решения оператора → эталон и обучение
sd.cmd feedback-export
```

Профиль (`--profile`) — тот же файл `configs/experiments/<имя>.yaml`, что и в оценке: модели и параметры для потока выбираются так же, как для эксперимента. Если в профиле задан `cycle_bundle` (пакет классификатора цикла **на «быстрых» признаках**), используется он, иначе — эвристика по длительности паузы (воркер предупреждает: она не отличает питьё и телефон от курения).

### Первый запуск

1. Скачать веса (`sd models get yolo26n-pose`), положить 2–3 коротких клипа в `streams/test-01-20261009T100000/`.
2. `sd monitor --streams streams --speed 0` — должны появиться тревоги там, где есть курение.
3. Сверить с offline: `sd recognize <клип>` для того же клипа — границы события должны совпасть с тревогой в пределах 1–2 с (в потоке нет склейки треков постфактум, см. ограничения).
4. Замерить скорость: воркер пишет время обработки камеры; для реального времени нужно ≥ `process_fps` (10) кадров/с на камеру на вашем железе.

## 4. Как устроен движок (`src/sd/realtime/engine.py`)

* **Вход** — `step(img, t)`: кадр и секунды потока. `pose_fn(img, t)` возвращает людей (`PoseTracker.step`, в тестах — синтетика). Детекции складываются в буфер (рамка, ключевые точки).
* **Раз в секунду потока** (`eval_every_sec`) на буфере пересчитываются ряд признаков и автомат циклов. Берутся только **закрытые и «осевшие»** циклы (конец старше `settle_sec = 1 с`), чтобы не принять недоотведённую руку за конец цикла; циклы, обрезанные началом буфера, игнорируются.
* **Оценка цикла** — `Scorer`: `HeuristicScorer` (эвристика) или `BundleScorer` (обученный пакет, быстрые признаки: кинематика, ритм, положение точек). Предмет на кропе, фото-модель и VLM в поток **пока не подключены** (дорого и требуют отдельной очереди, см. §8 руководства и план).
* **События** — `events.build_events` по регламенту: два цикла за 20 с (оба целиком в окне) или цикл + прямой признак; склейка одного человека ≤ 15 с; людей ниже 80 px не оцениваем (IGNORE).
* **Тревога** поднимается, когда выполнено правило **и** confidence ≥ порога профиля. `start_sec` события — начало подъёма руки в первом цикле (задним числом): метрика «задержка» мала, но сама тревога приходит в момент подтверждения — **типично через 5–15 с после начала курения** (две затяжки) плюс ≈ 1–2 с «оседания». Быстрее, не нарушив регламент, невозможно.
* **Обновления**: событие может продлиться (третий цикл) — приходит `update` (в базе обновляются конец и уверенность, **решение оператора сохраняется**); через `merge_gap` (15 с) без новых циклов — `close`.
* **Память ограничена**: буфер 90 с, кольцо кадров для миниатюр и клипов 45 с (JPEG 640 px, ≈ 10 МБ), состояние событий очищается от старого — поток можно гонять сутками (`test_engine_state_stays_bounded_over_long_stream`).

### Ограничения и риски (читать до демонстрации)

| что | последствие | как обойти / план |
|---|---|---|
| **Нет склейки треков постфактум** (в offline она есть, `tracks.stitch_tracks`) | при смене ID одного человека событие может раздробиться (1 TP + 1 FP) или не собраться | `track_buffer_sec` 3 с у трекера; план — онлайн-склейка по рамке и времени |
| Сглаживание признаков **центрировано** (медиана и Савицкого–Голея смотрят вперёд на 0.2–0.5 с) | тревога запаздывает на это время; на метрику не влияет | заложено в «оседание» |
| В потоке только быстрые признаки | на питьё/телефон хуже offline-режима с предметом и VLM | отдельная очередь VLM для «серой зоны» (план) |
| Один воркер обрабатывает камеры **последовательно** | при N камерах скорость делится | запускать по процессу на камеру (`--camera`) или GPU-батчинг (план) |
| После перезапуска воркера состояние потока теряется | жест на стыке перезапуска может не засчитаться; обработанные фрагменты не повторяются | допустимо для MVP |
| Время камеры = время начала из имени папки + длительности | при пропусках кадров в файлах дрейф | для реальных потоков — метки времени источника |

## 5. Хранилище (`outputs/monitor/monitor.db`, SQLite WAL)

* `cameras` — камера, район, индекс, папка, время начала, статус (`processing`/`idle`), последняя активность, обработано секунд.
* `chunks` — обработанные фрагменты со смещением от начала потока (перезапуск продолжает с первого необработанного).
* `alerts` — тревога: ключ события `<камера>:<ID человека>:<начало>`, время события (абсолютное) и время поднятия, уверенность, рамка человека, правило и текстовое объяснение («2 цикла за 14 с, предмет у рта»), `status` (`new` → `confirmed` | `false` | `unsure`), оператор, время решения, заметка, путь к миниатюре и клипу, отпечаток профиля, признак `demo`.

Путь к базе — `SD_MONITOR_DB` (по умолчанию `$SD_OUTPUTS/monitor/monitor.db`). Пишет воркер, читает приложение — разные процессы; для нескольких машин нужна серверная БД (план).

## 6. Приложение оператора (`sd app`, порт 8502)

Только то, что нужно для работы с камерами; инструменты разработчика — в `sd ui`.

* **Дашборд**: «Ждут решения», «Подтверждено сегодня», «Ложных сегодня», «Точность тревог» (подтверждено / (подтверждено + ложных)), число камер.
* **Лента тревог**: карточка = кадр с рамкой человека, район и камера, время события, что сработало, уверенность, кнопки **Подтвердить / Ложная / Открыть**. Фильтры: статус (по умолчанию «ждёт решения»), район, камера, период, минимальная уверенность. Автообновление раз в 5 с с всплывающим уведомлением о новых тревогах.
* **Карточка тревоги**: клип ±5 с, уверенность, правило и объяснение, решение («Подтвердить / Ложная / Не уверен»), заметка, другие тревоги этой камеры, блок «Для разбора разработчиком» (фрагмент, секунда в нём, ключ события, отпечаток профиля — по ним событие находится на странице «Просмотр» `sd ui`).
* **Камеры**: состояние (обработка / ожидание / нет данных), сколько обработано, число тревог и ждущих решения.
* **Журнал**: принятые решения с выгрузкой CSV.

Обратная связь: `sd feedback-export` (или кнопка на странице «Мониторинг» `sd ui`) переносит решения в `labels/events_gt.csv` — подтверждённые как POSITIVE с рамкой, ложные как NEGATIVE (**сложные негативы**); времена пересчитываются в секунды фрагмента, повторный экспорт дубликатов не создаёт, файл эталона защищён блокировкой от одновременной записи с разметчиком.

**Чего в каркасе нет сознательно:** авторизации и ролей (оператор — поле имени), звуковых оповещений и интеграций (webhook/MQTT), просмотра живого видео камеры, нескольких площадок, SLA на реакцию. Это следующий этап (см. план в [AUDIT_AND_CHANGES.md](AUDIT_AND_CHANGES.md)).

## 7. Подключение настоящего потока

`realtime/sources.py::CaptureSource(url)` читает RTSP/веб-камеру через OpenCV в отдельном потоке с очередью 3 кадра: когда обработка не успевает, старые кадры выбрасываются (задержка не растёт, §8.3). Он не подключён к команде `sd monitor` (нужны реальная камера и решение по именованию); подключение — это цикл `for img, t in src.frames(): engine.step(img, t)` и запись тревог через `process_stream`-подобную обвязку. Протестировать на файле с реальной скоростью — `--speed 1`.
