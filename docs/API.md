# Бэкенд платформы и API

> 15 октября 2026. Платформа — единственное веб-приложение проекта: единый API с входом и ролями, БД с миграциями, поток обновлений, доступ к функциям Dev Studio и веб-интерфейс `/app` ([WEB_UI.md](WEB_UI.md)). Пакет `src/sd/server`. Запуск — `sd app` (для работы на одном компьютере, без входа) или `sd serve` (сервер, вход обязателен); интерактивная документация API — `/docs` (OpenAPI — `/api/v1/openapi.json`).
> Старое веб-приложение (стандартный HTTP-сервер на порту 8502 и отдельное хранилище `monitor.db`) удалено: его логика перенесена в `server/services`, интерфейс заменён на `/app`. Dev Studio (`sd ui`, порт 8501) — отдельный интерфейс разработчика на Streamlit.

## 1. Зачем и как устроено

До этого у проекта было два интерфейса без общей основы: Streamlit для разработчика и самодельный HTTP-сервер для оператора (без входа и ролей, с хранилищем-SQLite без миграций). Для веб-версии нужны:
- один API, к которому подключатся и веб, и десктоп, и внешние системы;
- вход, роли и журнал действий;
- БД, схема которой развивается миграциями и переносится с SQLite на PostgreSQL без переписывания кода;
- доступ к функциям разработчика без Streamlit.

```
 браузер (/app) / скрипты                воркер потока (sd monitor)        Dev Studio (sd ui)
          │  HTTP(S), Bearer-токен / cookie          │ SqlAlertStore                │ SqlAlertStore (обратная связь)
          ▼                                          ▼                              ▼
 ┌─ sd app / sd serve (FastAPI) ─────────────────────────────────────────────────────────────┐
 │ static/    веб-интерфейс /app (vanilla JS, без сборки)                                    │
 │ routers/   system · auth · users · cameras · alerts · analysis · dev      (роль на каждом) │
 │ services/  users · alerts · cameras · audit · artifacts · reports                         │
 │            videos (источники, воспроизведение, разбор) · devtools (профили, реестр)       │
 │ deps.py    сессия БД · пользователь · require(role) · аудит                               │
 └───────┬───────────────────────────────────────────────────────┬───────────────────────────┘
         │ SQLAlchemy 2 + Alembic                                │ использует модули проекта
         ▼                                                       ▼
   SQLite (файл) / PostgreSQL                 sd.runner · sd.profiles · sd.solver · sd.realtime.replay
   users · api_tokens · audit_log             sd.tasks · sd.experiments · sd.compare · sd.labels_history · sd.release
   cameras · chunks · alerts · alert_reviews
```

Принципы:
- **Тонкие маршруты.** Маршрут разбирает запрос, проверяет роль и возвращает схему; логика — в `services/` и модулях проекта. Поэтому добавлять экраны и клиентов можно, не трогая ядро.
- **Одно хранилище.** `SqlAlertStore` — единственное хранилище тревог: в него пишут воркер, демо-данные и обратная связь, его читают API, интерфейс и Dev Studio. По умолчанию это один файл `outputs/platform/platform.db`, поэтому `sd monitor` и `sd app` видят одни и те же тревоги без настройки.
- **Схема только через миграции.** `create_all` нигде не вызывается; приложение при старте само применяет недостающие миграции.
- **Права проверяются на сервере**, интерфейс лишь скрывает недоступное.

## 2. Быстрый старт

```bash
pip install -r requirements.txt                     # fastapi, sqlalchemy, alembic уже в списке
sd db upgrade                                       # создать/обновить схему (приложение делает это и само при старте)
sd user create admin --role admin                   # пароль спросят без отображения; требования: ≥ 8 знаков, строчные и заглавные буквы, цифра
sd app                                              # для работы на этом компьютере: http://127.0.0.1:8502/app/ (вход отключён)
sd serve                                            # сервер: http://127.0.0.1:8503/app/ · API: http://127.0.0.1:8503/docs (вход обязателен)
```

`sd app` и `sd serve` — один и тот же сервер с разными настройками по умолчанию. `sd app`: порт 8502, вход отключён (администратор `local`), загрузка файлов и подключение папок разрешены, `--open` открывает браузер; при `--host 0.0.0.0` вход включается сам, `--login` включает его и на локальном адресе. `sd serve`: порт 8503, вход обязателен, `--no-auth` допустим только на локальном адресе, `--reload` — для разработки.

Локальная работа без входа (все запросы — администратор `local`; только при привязке к 127.0.0.1):

```bash
sd serve --no-auth
```

Из сети (вход обязателен, загрузка файлов и подключение папок отключены):

```bash
SD_ADMIN_USER=admin SD_ADMIN_PASSWORD='...' sd serve --host 0.0.0.0     # первый администратор создаётся при старте, если пользователей нет
```

Docker: `SD_ADMIN_USER=admin SD_ADMIN_PASSWORD='...' docker compose up web` (порт публикуется только на 127.0.0.1; образ ни разу не собирался — см. [OPERATIONS.md](OPERATIONS.md)).

Пример сценария по HTTP:

```bash
TOK=$(curl -s localhost:8503/api/v1/auth/login -H 'Content-Type: application/json' -d '{"username":"admin","password":"..."}' | python -c "import sys,json;print(json.load(sys.stdin)['access_token'])")
curl -s "localhost:8503/api/v1/alerts?status=new&limit=10" -H "Authorization: Bearer $TOK"
curl -s -X POST localhost:8503/api/v1/alerts/5/review -H "Authorization: Bearer $TOK" -H 'Content-Type: application/json' -d '{"status":"false","reason":"drink","note":"пил воду"}'
```

## 3. Настройки

Переменные окружения (и файл `.env`); разбор — `sd.server.settings.Settings.from_env`.

| переменная | по умолчанию | что |
|---|---|---|
| `SD_DB_URL` | SQLite `outputs/platform/platform.db` | строка подключения SQLAlchemy. PostgreSQL — `postgresql+psycopg://user:pass@host/db` (драйвер ставится отдельно) |
| `SD_SECRET_KEY` | создаётся в `outputs/platform/secret.key` | секрет подписи токенов доступа. При нескольких экземплярах API задайте одинаковый явно |
| `SD_AUTH` | `on` | `off` — вход отключён (все запросы от имени `local`, роль admin). В сети не использовать: `sd serve` откажется |
| `SD_TOKEN_TTL_MIN` | 720 | срок жизни токена доступа, минут |
| `SD_CORS` | пусто | разрешённые источники браузера через запятую; пусто — CORS выключен |
| `SD_API_DOCS` | 1 | `0` скрывает `/docs`, `/redoc` и OpenAPI |
| `SD_UI` | 1 | `0` не раздаёт веб-интерфейс (`/app`): сервер остаётся чистым API |
| `SD_ADMIN_USER`, `SD_ADMIN_PASSWORD` | — | создать администратора при старте, если пользователей ещё нет |

`SD_DB_URL` читают все: API, воркер (`sd monitor`), демо-команды и Dev Studio — они всегда работают с одной БД (см. раздел 7). Без переменной это SQLite-файл `outputs/platform/platform.db`.

## 4. Вход и роли

**Токен доступа.** `POST /api/v1/auth/login` с именем и паролем возвращает `access_token` (подписанная строка со сроком жизни). Дальше — заголовок `Authorization: Bearer <токен>`. Смена пароля, блокировка и роль пользователя увеличивают его `token_version`: все выданные ему токены перестают действовать сразу; `POST /auth/logout-all` делает то же по требованию.

**API-токены** для скриптов и интеграций: `POST /auth/tokens` (показывается один раз; в БД хранится только sha256), срок жизни необязателен, отзыв — `DELETE /auth/tokens/{id}`. Они работают во всех маршрутах так же, как токен доступа, и действуют, пока активен владелец.

**Где принимается токен:**
1. заголовок `Authorization: Bearer …` — всегда;
2. cookie `sd_token` (если при входе передано `"cookie": true`) — **только для GET/HEAD**: тег `<video>` и `<img>` заголовков не шлют, а изменяющие запросы по cookie не принимаются, поэтому CSRF невозможен;
3. параметр `?access_token=` — только для GET-маршрутов `/media/*`, `/alerts/{id}/thumb|clip` и `/events` (EventSource и теги медиа не умеют заголовков). Токен в адресе попадает в журналы прокси — для них лучше короткоживущий токен.

**Защита входа:** пароль хранится как scrypt с индивидуальной солью; проверка несуществующего имени занимает столько же времени; после 5 неудачных попыток подряд с одного адреса на одно имя вход блокируется на 60 с (ответ 429 с `Retry-After`; счётчик в памяти процесса); неудачные входы пишутся в журнал действий.

**Роли** (каждая включает все предыдущие):

| роль | что может |
|---|---|
| `viewer` | смотреть камеры, тревоги, статистику, видео, результаты разбора |
| `operator` | + принимать решения по тревогам, ставить разбор видео в очередь, загружать видео (при локальной привязке) |
| `developer` | + интерфейс разработчика: профили, журнал прогонов и пометки, задачи, версии разметки, выпуски |
| `admin` | + пользователи, камеры, источники, демо-данные, журнал действий |

Нельзя понизить, заблокировать или удалить последнего активного администратора.

**Файлы и медиа:** `GET /alerts/{id}/thumb|clip` и `GET /media/video/{fid}` отдаются с поддержкой `Range` (перемотка); пути файлов тревог ограничены каталогом `outputs/`, остальные считаются отсутствующими. Видео, которое браузер не играет, перекодируется один раз; пока копия готовится, ответ — `202` с состоянием и процентом (`/media/status`).

**Поток обновлений** `GET /events` (Server-Sent Events): события `ready` (курсоры), `alert.new` (новая тревога), `alert.review` (решение оператора); каждые ~15 с без событий — комментарий `: ping`. Параметры: `since_alert`, `since_review` (курсоры; без них — только новое), `timeout` (сколько секунд держать соединение, по умолчанию 60) и `interval` (период опроса БД). После закрытия клиент переподключается с последними курсорами из событий. Реализация — опрос БД; для десятков операторов этого достаточно, для сотен — заменить на рассылку из очереди (см. раздел 9).

### 6.1. Таблицы

| таблица | назначение | ключевые поля |

| `alerts` | тревоги | `key` (уникален: камера:человек:начало), `t_abs`, `confidence`, `box` (JSON), `status`, `state`, пути `thumb`/`clip`, `fingerprint` профиля |
| `alert_reviews` | история решений (неизменяемая) | `alert_id`, `status`, `reason`, `note`, `reviewer_id`/`reviewer_name`, `created_at` |

Решение оператора — это новая строка `alert_reviews`; в `alerts.status` остаётся последнее. Продление события воркером решение не сбрасывает. `alerts.camera_id` — мягкая ссылка (без внешнего ключа): воркер пишет тревоги независимо от порядка заведения камер. Статусы и роли защищены `CHECK`-ограничениями.

**Время.** Все времена в БД — локальное «наивное» время машины, как у камер-папок и прежней базы; `t_abs` — время события по часам камеры. Единственный источник времени — `sd.server.clock`; переход на UTC — замена этой функции и миграция данных. В API времена отдаются в ISO `YYYY-MM-DDTHH:MM:SS`.

### 6.2. Миграции (Alembic)

Скрипты лежат в `src/sd/server/migrations/versions`; управление — командами `sd db …` (файла `alembic.ini` нет: путь и URL задаются программно, `sd.server.migrate`).

| команда | что делает |
|---|---|
| `sd db current` | версия схемы в БД и последняя доступная |
| `sd db upgrade [версия]` | применить миграции (по умолчанию до `head`) |
| `sd db downgrade [версия] --yes` | откатить (по умолчанию на одну назад; `base` — все таблицы платформы) |
| `sd db history` | цепочка миграций |
| `sd db revision -m "…"` | создать миграцию автогенерацией (БД должна быть на актуальной версии); `--empty` — пустая заготовка |
| `sd db stamp [версия]` | пометить БД версией без выполнения (БД создана вручную) |
| `sd db import-legacy [файл]` | перенести данные из прежней `monitor.db` |

Цепочка сейчас: `0001_identity` (пользователи, токены, аудит) → `0002_monitoring` (камеры, фрагменты, тревоги, история решений).

**Как менять схему:**
1. Правка `src/sd/server/models.py`.
2. `sd db revision -m "что изменилось"` → открыть созданный файл, проверить (типы, имена ограничений, значения по умолчанию для существующих строк, `downgrade`).
3. `sd db upgrade`; запустить тесты — `test_migrations_up_down_and_no_drift` сравнивает схему после миграций с моделями и падает при расхождении, `test_migrations_render_for_postgresql` проверяет, что миграции описываются корректным SQL для PostgreSQL.
4. Выпущенные миграции не правят — добавляют новую. Для новых `NOT NULL`-колонок в таблицах с данными — `server_default` или промежуточная заливка.

SQLite не умеет менять колонки напрямую — `env.py` включает пакетный режим (`render_as_batch`), поэтому одни и те же миграции работают и в SQLite, и в PostgreSQL.

**Масштабирование БД.** Для одного узла достаточно SQLite (WAL, ожидание блокировки 30 с, воркер и API — разные процессы). Для нескольких площадок и узлов — PostgreSQL: задайте `SD_DB_URL`, установите драйвер (`pip install "psycopg[binary]"`), выполните `sd db upgrade`, при необходимости `sd db import-legacy`. Код от СУБД не зависит; отдельная проверка на живом PostgreSQL не выполнялась (см. раздел 11).

**Резервные копии.** SQLite: копия файла при остановленных процессах или `sqlite3 platform.db ".backup копия.db"` на ходу. PostgreSQL — `pg_dump`. Перед `sd db upgrade` на боевых данных — копия.

## 7. Воркер, хранилище и перенос данных

- **Хранилище.** `server/store.py`, класс `SqlAlertStore` — единственное хранилище тревог (камеры, обработанные фрагменты, тревоги, история решений). Его создают без аргументов (`SqlAlertStore()`): БД берётся из `SD_DB_URL`, иначе это файл `outputs/platform/platform.db`; схему конструктор доводит миграциями. Тест `test_sql_store_lifecycle` проходит весь жизненный цикл тревоги, `test_worker_writes_to_platform_db_and_api_sees_it` прогоняет настоящий воркер.
- **Воркер** (`sd monitor`), `sd monitor-demo`, `sd feedback-export` и Dev Studio («Данные → Обратная связь оператора») работают с тем же хранилищем: тревога, записанная воркером, сразу видна в интерфейсе, решение оператора — сразу в эталоне.
- **Перенос из старой базы.** До объединения хранилищ воркер писал в отдельный SQLite-файл `outputs/monitor/monitor.db`. Если в нём есть данные, один раз выполните `sd db import-legacy [файл]`: команда читает файл только для чтения, сохраняет идентификаторы тревог (на них ссылаются каталоги миниатюр и клипов `outputs/monitor/alerts/<id>`), создаёт первую строку истории для решённых тревог и пропускает уже перенесённое (повтор безопасен). Новые данные в `monitor.db` больше не пишутся.
- **Обратная связь в обучение:** `sd feedback-export` и «Данные → Обратная связь оператора» работают с любым хранилищем.

## 8. Соглашения API

- **Ошибки:** JSON `{"detail": "..."}`. 401 — нет входа или токен недействителен; 403 — мало прав; 404 — нет объекта; 409 — конфликт; 422 — неверные данные (в том числе ограничения схем); 429 — слишком много попыток входа; 500 — внутренняя ошибка (подробности только в журнале сервера). Ошибки прежних модулей приводятся к кодам: `NotFound`/`FileNotFoundError` → 404, `PermissionError` → 403, `FileExistsError` → 409, `ValueError`/`KeyError` → 400.
- **Страницы:** `GET /alerts` и `GET /audit` возвращают `{items, total, limit, offset}`; `limit` ≤ 500.
- **Фильтры тревог:** `status` (можно несколько), `camera`, `district`, `city`, `min_conf`, `since`, `until`, `demo`, `state`, `oldest_first`.
- **JSON:** результаты прежних модулей проходят `jsonutil.clean` (NaN → `null`, numpy и даты → стандартные типы).
- **Заголовки:** `X-Request-ID` (возвращается или принимается), `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store` для API.
- **Версионирование:** префикс `/api/v1`; несовместимые изменения — в `/api/v2`, `v1` остаётся на время перехода.

## 9. Как расширять

**Новый ресурс.**
1. Модель в `models.py` → миграция (`sd db revision`).
2. Схемы в `schemas.py`.
3. Логика в `services/<имя>.py` (функции над `Session`, без HTTP).
4. Маршруты в `routers/<имя>.py` с `Depends(deps.<роль>)`; подключить в `app.create_app`.
5. Запись в журнал действий: `deps.audit(s, request, me, "ресурс.действие", "ресурс", id, **детали)`.
6. Тест в `tests/test_server.py` (фикстура `env` даёт клиент, БД и пользователей по ролям); таблица маршрутов в этом документе строится по маршрутам.

**Новая роль.** Добавить в `models.ROLES` (порядок = права) и в CHECK через миграцию; зависимость `deps.require("роль")`.

**Доступ по объектам (город, район, смена).** Сейчас права — по ролям на весь сервис. Модель данных готова к разграничению: у камер есть `city`/`district`; достаточно таблицы `user_scopes` (пользователь → город/район) и фильтра в `services.alerts.filtered` и `services.cameras`.

**Фоновые задачи.** Разбор видео идёт очередью `VideoService` в памяти процесса, задачи разработчика — процессами `sd.tasks` (файловое состояние). При масштабировании на несколько узлов их состояние переносят в таблицу `jobs` и исполнитель-процесс; интерфейс маршрутов при этом не меняется.

**Рассылка событий.** Вместо опроса БД в `/events` — PostgreSQL `LISTEN/NOTIFY` или Redis: меняется только генератор в `routers/alerts.events`.

**Новый сценарий видеоаналитики.** Тревоги уже несут `rule` и `explain`; для нового сценария добавьте значение `rule`, поле сценария (миграция) и фильтр — остальное (решения, история, поток, статистика) работает без изменений.

**Клиент.** Из `/api/v1/openapi.json` генерируется типизированный клиент (например, `openapi-typescript`). Веб-интерфейс `/app` уже работает на `/api/v1` ([WEB_UI.md](WEB_UI.md)); тест сверяет каждый его вызов с OpenAPI. Прежнее приложение оператора (`sd app`, порт 8502) остаётся на своих маршрутах.

## 10. Безопасность: что сделано и чего нет

Сделано:
- вход и роли на каждом маршруте (кроме `/health`, `/auth/login`, `/auth/logout`); права проверяются на сервере;
- пароли — scrypt с солью; токены доступа подписаны и отзываются; API-токены хранятся как sha256;
- CSRF исключён конструкцией: cookie только для чтения, изменения — только с заголовком;
- интерфейс `/app` отдаётся с политикой `Content-Security-Policy` (только свои ресурсы, без внешних адресов и фреймов), без `innerHTML` и `eval` в коде ([WEB_UI.md](WEB_UI.md), раздел 7);
- блокировка подбора пароля, неудачные входы в журнале;
- журнал действий: вход, пользователи, решения, камеры, профили, задачи, источники; пароли и токены в него не попадают;
- пути файлов тревог ограничены `outputs/`; идентификаторы видео непрозрачны и не выходят за разрешённые корни; имена профилей и прогонов проходят проверку; задачи — только белый список `tasks.CATALOG`;
- загрузка файлов и подключение папок работают только при привязке к 127.0.0.1 (`allow_fs`), в сети — 403;
- `sd serve --no-auth` отказывается работать при привязке не к 127.0.0.1.

Не сделано, требует решения при внедрении:
- **HTTPS.** Сервер сам TLS не терминирует: за обратным прокси (nginx, Caddy, облачный балансировщик) с сертификатом; cookie получают флаг `Secure`, когда запрос пришёл по `https`.
- **Счётчик попыток входа** хранится в памяти процесса: при нескольких процессах лимит не общий (общий — таблица или Redis).
- **Секрет подписи** при нескольких экземплярах задаётся явно одинаковым (`SD_SECRET_KEY`).
- **Роли без разграничения по объектам** (см. раздел 9), двухфакторного входа и интеграции с внешним каталогом (LDAP/OIDC) нет.
- **Лицензия Ultralytics (AGPL-3.0)** и риски распознавания — [REPORT.md](REPORT.md), раздел 7.

## 11. Как проверено и ограничения

Проверено автоматически (`tests/test_server.py` — 29 тестов, `tests/test_videos.py` — видео и разбор, `tests/test_web_ui.py` — интерфейс и сводка отчётов, плюс тесты воркера и хранилища в `tests/test_realtime_pipeline.py`):
- миграции: подъём, откат, повторный подъём, отсутствие расхождения с моделями, SQL для PostgreSQL, CHECK-ограничения и каскады;
- безопасность: пароли, токены (подпись, срок), роли, правила последнего администратора;
- видео и разбор (`test_videos.py`): папки и загрузка любого формата, воспроизведение в H.264 и VP9 с `Range`, очередь разбора и живой вывод кадров, журнал конфигураций, экспорт видео с разметкой, профили разработчика;
- API: вход, блокировка подбора, отзыв токенов при смене пароля и блокировке, cookie только для чтения, токен в адресе только для медиа, матрица ролей, API-токены, режим без входа, пользователи, камеры (валидация и показатели), тревоги (фильтры, страницы, история решений, пакетные решения, журнал CSV, файлы с `Range` и ограничением каталога), поток обновлений, разбор видео и источники (в том числе отказ от загрузки в сети), конечные точки разработчика, демо-данные;
- хранилище: жизненный цикл тревоги; воркер пишет в БД платформы, а API это видит; БД по умолчанию и из `SD_DB_URL`; перенос из старой базы идемпотентен и не меняет исходник;
- CLI: `sd db`, `sd user`, `sd serve --no-auth` в сети; запуск `sd app` проверен вручную (вход отключён, демо-тревоги из `sd monitor-demo` видны в интерфейсе).

Живая проверка: сервер запущен командами `sd serve` и `sd app` на отдельной БД; вход по токену, демо-тревоги, миниатюра с `Range` (206), решение с причиной и история, поток обновлений, `/docs` и OpenAPI — работают.

**Не проверено / ограничения:**
- PostgreSQL на живом сервере не запускался (миграции проверены как SQL для этого диалекта; драйвер не установлен);
- Docker-образ с сервисом `web` не собирался;
- нагрузка (сотни операторов и камер) не измерялась; `/events` опрашивает БД;
- RTSP-источники в мониторе по-прежнему не подключены (поле `cameras.source_url` — резерв).
